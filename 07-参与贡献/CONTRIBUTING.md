# 参与贡献

> 这个包的价值全部来自「真实踩过的坑」。你踩到了，写下来，下一个人就少踩一次。

## 最有价值的三种贡献

### 1. 新的坑（最高价值）

格式固定，方便我直接并进红线清单：

```markdown
### 现象
（用户看到什么，越具体越好）

### 根因
（为什么会这样，不知道就写"疑似"，不要编）

### 解法
（怎么修，最好给代码）

### 环境
（基础库版本 / 开发者工具版本 / 真机型号 / 云开发）
```

提到 `05-红线/技术红线.md` 的对应章节。

### 2. 「我在阶段 X 卡住了」

这比功能建议有用得多。写清：
- 你在哪个阶段
- AI 的哪句话让你卡住了（原话）
- 你希望它怎么问

阶段引导的话术就是这么一轮轮改出来的。

### 3. 规则变了

平台规则、类目、API 会变。如果你发现包里某条已经过时：
- 附上官方文档链接
- 说明是哪一天变的

---

## 提 PR 之前

- [ ] 只改一个东西（一个坑 / 一个问题 / 一个阶段）
- [ ] Markdown 能正常渲染（表格对齐、代码块标语言）
- [ ] 没有真实密钥、AppID、云环境 ID、公司名、真实用户数据
- [ ] 中文，短句，和现有文档的语气一致（结论先行，不写套话）

## 文档语气约定

| 要 | 不要 |
|----|------|
| 「先给结论：能做」 | 「关于这个问题，我们需要综合考虑……」 |
| 「这条会浪费你半小时」 | 「请注意此问题可能导致效率降低」 |
| 具体数字（200KB、20s、112rpx） | 「较大」「较长」「适当」 |
| 承认不确定（「需你核对官方文档」） | 编一个看起来合理的答案 |

## 不建议的贡献

- 加更多文件（这个包已经有 20+ 个文件，再加会让人不想打开）
- 把 Word/PDF 版本塞进来（GitHub 上 md 更好维护，转换可以本地做）
- 加依赖（`check.js` 故意零依赖，就是为了别人 clone 下来能直接跑）
- 改 LICENSE

## 提交方式

1. Fork
2. 新建分支：`fix/wxss-var-example` / `feat/stage4-bug-table`
3. 提交信息：`fix: WXSS 变量那条补一个错误示例`
4. 提 PR，描述里写清「改了什么 / 为什么」

## 发现问题但不想写 PR

开 Issue 就行，写清现象和你的环境。我看到了会整理进去。
